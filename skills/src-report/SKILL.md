# 漏洞报告写作规范

## 0. 报告结构（必须齐全）

```markdown
# 报告标题：[等级] 资产 - 漏洞类型
（例：[高危] example.com 登录接口 SQL 注入）

## 1. 概要
- 漏洞类型：
- 危险等级：严重/高危/中危/低危
- CVSS 3.1：AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N（7.5）
- 影响资产：https://example.com/login
- 发现时间：YYYY-MM-DD

## 2. 复现步骤
1. 访问 ...
2. 发送请求：
   ```http
   POST /login HTTP/1.1
   Host: example.com
   ...
   ```
3. 观察响应：...（关键报文/截图说明）

## 3. 证据
- 原始请求/响应片段
- 截图说明（含时间、URL、关键数据）
- 工具输出（nuclei/sqlmap 关键行）

## 4. 影响分析
攻击者可 ...（不夸大：能读什么/能执行什么/范围多大）

## 5. 修复建议
- 具体措施（参数化查询/升级版本/配置项）
- 修复后验证方法

## 6. 备注
- 前置条件
- 已排除的误报
- 复测建议
```

## 1. 等级判定参考

| 等级 | 典型场景 |
|---|---|
| 严重 | RCE、任意文件读写、数据库管理员权限、大量敏感数据泄露 |
| 高危 | SQL注入（可读库）、认证绕过、SSRF 打内网、越权（管理员） |
| 中危 | 存储型XSS、任意用户越权、敏感信息泄露（中等） |
| 低危 | 反射XSS、信息泄露（低敏感）、配置缺陷 |

## 2. 复现步骤写法（高质量）

- 编号、可照做、含具体参数与完整请求
- 截图必须**有时间**和**目标 URL**
- 敏感数据打码（不要贴完整数据库/密码）
- 不要写"然后黑客就控制了系统"这类含糊话

## 3. 证据要求

- 原始 HTTP 报文优先（curl / Burp 保存）
- 工具输出截关键行，不要贴满屏
- 每个结论都有证据支撑（"响应返回了 200 + 用户邮箱"）

## 4. 平台差异

| 平台 | 侧重 |
|---|---|
| 补天 | 中文标题、复现步骤、截图证明、影响、修复建议 |
| 漏洞盒子 | 漏洞描述（原理）+ 复现 + 修复方案 |
| HackerOne | 英文、Title/Summary/Steps/Impact/Remediation |
| 交付给客户 | 正式报告（封面+目录+风险评级+整改清单） |

## 5. 常见错误

- ❌ 只截图不给原始报文
- ❌ 影响夸大（"可获取全部数据"但实际只回显了一行）
- ❌ 步骤不可复现（少了 header/cookie）
- ❌ 报告里泄漏客户其他信息（脱敏不全）
- ❌ 等级定错（低危报成高危，影响信任）
